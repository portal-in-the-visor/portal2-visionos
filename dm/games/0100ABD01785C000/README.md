Base 1.0.0 (`v0`), SDK 13.3.0. Pinned upstream commit `f4a24b8794f35067d1cd057ae5fcb999fbfb07cf`. No update supplied or tested. Valve's Source engine in NVIDIA Lightspeed Studios' Switch port.

## Modules and files

ExeFS: main, sdk, subsdk0 (GLSLC), subsdk1 (OpenGL driver), rtld. Unlike the original Portal profile, there is no subsdk2 or video_nx.nro. NROs: bsppack, client, datacache, engine, filesystem_stdio, inputsystem, launcher, localize, matchmaking, materialsystem, scenefilecache, server, shaderapiempty, soundemittersystem, studiorender, tier0, vgui2, vguimatsurface, vphysics, vscript, vstdlib.

`main`'s SDL EGL imports alone suggest GL, but the NRO imports and observed NVN rendering establish NVN. The existing packing script corrects the provisional graphics choice after collecting NROs. No game-specific binary patch was added.

`game.zip` is 7,702,307,263 bytes with 46,587 members and 1,267 `.nvsb` members. `nxcontent/rom_boot_params.txt` selects portal2 and shader-save filesystem, disables mouse, and sets portal stencil depth 2. Game files and their extracted content remain outside the repository.

## Portal boundary rendering (open)

The user reached the portal gun, picked up a cube, and saved. After a restart with only the Xbox controller assigned player 1, the user reported responsive controls. This does not prove the earlier stale-input fault fixed.

A screenshot and live frame F29329 show the portal view outside the oval, filling a rectangular surface. The pass capture has a six-index mask draw in pass 478254: vertex `dab5432420688429`, fragment `a49ede2501bd153c`, stencil ALWAYS/REPLACE reference 1, color write mask zero, depth writes enabled. The translated fragment computes a circular test from its UVs and writes its result as alpha 0 or 1; it has no discard. The next pass tests stencil EQUAL reference 1.

Fixed (2026-10-30, Mac): missing fixed-function alpha testing. `hle_nvn.c:nvnColorStateSetAlphaTest` records the function, but `nvnCommandBufferSetAlphaRef` drops the reference and explicitly logs that alpha testing is unsupported. `nvn_mtl.m` does not consume `S.color.alpha_func`. If enabled on this mask draw, absent alpha rejection would let its entire rectangle update depth/stencil. Confirmed by the alpha-observe pass dump (`run/alpha-observe.log`, frame F4899, draw 124248, same vs/fs pair): `alpha_func=5` (GREATER), `alpha_ref=0.498039`, stencil front/back ALWAYS/REPLACE. Without alpha rejection the whole quad writes stencil, which matches the rectangular portal view.

Fix in progress (uncommitted): `hle_nvn.c` records `OP_ALPHA_REF`; `nvn_mtl.m:draw_` binds an immutable per-draw {function, reference} at fragment buffer 15; `dmsh_build.py:fs_alpha_test` adds a `discard_fragment()` check on color 0 alpha and drops `[[early_fragment_tests]]`; chain `814c342b484e`. **Validated on the Mac** after a Terminal rebuild (`--platform mac --provisional`, host loaded `b-814c342b484e`): the user reports portals now clip to the oval. Opening-area timing afterwards: GPU p50 6.1 / p95 9.1 ms, 0 dropped frames per 300, footprint 2,152 MiB. Earlier attempt: the shader rebuild ran inside a sandbox that could not write `~/.cache/clang/ModuleCache`, so 841 of 1,186 shaders failed to compile, and the alpha-observe run loaded the old chain `b-a78f966a7b38` (unpatched shaders). `test_alpha_test.py` also failed only on "No Metal device" for the same reason. Rebuild from a normal Terminal before judging the fix. Performance note for VR: a compiled-in `discard_fragment()` disables early depth/HSR on every fragment shader even when the function is ALWAYS; if GPU time regresses, specialise with a function constant instead. Do not patch this one shader with a permanent hard-coded discard; preserve NVN state semantics.

The unrelated `SetRenderEnableConditional: the host draws anyway for now` warning also occurs and remains unassessed. Portal clipping is not validated for the Mac milestone or VR.

## VR camera hook (checkpoint 3, in progress)

- **Located through RTTI** (client.nro keeps typeinfo; its symbol table exports only 6 symbols): `11CViewRender` → vtable `client+0x1281fb0` (42 slots). Slot 5 `CViewRender::Render` `+0x374df8` calls slot 6 through `[vtable+0x30]` at `+0x3759d4`. Slot 6 `CViewRender::RenderView` `+0x39977c` takes `(this, const CViewSetup &view, const CViewSetup &hudView, int clearFlags, int whatToDraw)`, the Alien Swarm / Portal 2 signature, and copies `view` into `this+0x234` at once. Also found: `CPortalRender` vtable `client+0x12c8528`, `CHLClient` vtable `client+0x122f778`.
- **Hook:** observation gate 26 (`OBS_SOURCE_RENDERVIEW`, `dm/host/dm.h`) at the entry, registered in this profile's `patches.py` for client build `6f1172dd16fa27eb697921364f8a78cb`. `dm/host/hle_vrview.c` composes a head pose (`vr_view.h: vr_view_set_head`) into the view's angles (Source AngleMatrix/MatrixAngles, view = body × head) and origin. Only the rendered view changes; aim and movement keep the game's angles.
- **CViewSetup offsets verified** (Mac, `DM_VR_VIEW_DUMP=1`, `sp_a1_intro1`/`intro3`): width/height `+0x10`/`+0x18` = 1920/1080, fov `+0x68` = 106.26 (90 at 4:3), fovViewmodel `+0x6c`, origin `+0x70` (71.2, 2023.6, -354.0), angles `+0x7c` (3.6, 36.9, 0), zNear `+0x88` = 7, zFar `+0x8c`, aspect `+0x98` = 1.778. This matches portal2vr's PC `CViewSetup` (`L4D2VR/sdk/sdk.h`, size 0x104) field for field. The gate fired (`nro2: gates 11`). **Visually verified** with `DM_VR_VIEW_TEST=20` (four screenshots 1 s apart in `sp_a1_intro3`): the view sweeps left/right and up/down while the portal-gun viewmodel stays with the body aim, and portals keep their oval clipping under the rotated view.
- **portal2vr (ref/portal2vr, commit 310ac49, 2026-07-12) for stereo:** it hooks the same `RenderView` (vtable function, same five arguments) and calls the original twice, once per eye with its own render target and an eye origin (`VR::TraceEye`), after setting the HUD view's size/fov/aspect. It also sets the game's view angles from the HMD (`IVEngineClient::SetViewAngles`), so aim follows the head, and corrects yaw after portal teleports (origin jump > 35 units). Portals are then correct per eye because each eye is a full `RenderView`. An observation gate cannot call the original twice; stereo needs a second call path (a guest-side shim in the vtable slot, or a host call into the guest function).
- **visionOS limit:** ARKit (WorldTrackingProvider device anchors) delivers data only while an app has an immersive space open, and the iPad-compatible build has no ARKit or device motion at all (log: "no device motion"). So a tracked head in a flat window is not available on Vision Pro. Head pose arrives with the native visionOS target and CompositorServices immersive space (checkpoint 4).

## Stereo (checkpoint 4, in progress)

**Side-by-side stereo works on the Mac** (`DM_VR_STEREO=1`, `dm/host/hle_vrview.c`). The RenderView entry gate calls the same function (the object's vtable slot 6) for one eye, on a copy of the view, while a thread-local flag lets that call's own gate pass through. The gate then rewrites the game's view for the other eye, and the game's own call renders it. Each eye gets half the viewport, the same vertical FOV and an origin offset of ±IPD/2 along the view's right axis (2.76 units = 64 mm at portal2vr's 43.2 units/m). Each eye is a full RenderView, so portals recurse from that eye's origin; screenshots show correct oval portals and a viewmodel in both eyes.

- **Black world, found and fixed:** RenderView leaves the material system's current render target changed. Logged: before our call NULL (the back buffer), after it 0x70e55efd90. The game's call then drew its world straight into the back buffer and the final copy left both eyes black. The pass dump showed eye 1 into the full-frame texture (ser 13) and eye 2 into the back buffer (ser 2). The fix reads `GetRenderTarget` before our call and `SetRenderTarget`s it back afterwards, through `materials` at `client+0x1641288` → `GetRenderContext` (vtable `+0x390`) → `IMatRenderContext` `BeginRender +0x10`, `EndRender +0x18`, `Release +0x08`, `SetRenderTarget +0x30`, `GetRenderTarget +0x38`. These slots were confirmed in materialsystem.nro's `CMatRenderContext`/`CMatQueuedRenderContext` vtables (slot 6 → `SetRenderTargetEx(0, tex)`, slot 7 → top of the render-target stack). The fix runs only when the vtable's slot 6 is `client+0x39977c`. `DM_VR_RT_RESTORE=0` reproduces the black frame.
- **Diagnostics** (all reread every 30 views, so `env KEY=VALUE` in the DM_CTL file switches them live): `DM_VR_STEREO` 0 off / 1 side by side / 2 one eye's viewport only / 3 two full-frame renders / 4 one viewport without the FOV change; `DM_VR_DIAG_EYE`, `DM_VR_FIRST_EYE`, `DM_VR_CLEAR_FIRST` / `DM_VR_CLEAR_SECOND` (hex masks on the clear flags; the game passes 0x22, whatToDraw 0x3), `DM_VR_IPD`.
- **Cost, Mac M3 Pro, `sp_a1_intro3`, two 960×1080 eyes:** GPU p50 7.4 / p95 9.0 ms (one 1920×1080 view: about 6 / 9). Frame work p95 rose to about 22 ms: the second RenderView costs main-thread CPU, so some frames now miss 60 Hz.
- **Open:** the HUD (crosshair) is drawn once across the whole frame, at the seam; it needs per-eye or panel placement (checkpoint 6). The back-buffer resolution (1920×1080) limits each eye to 960×1080. Headset numbers are still to be measured.

### Native visionOS app and immersive view

- **Native app:** `dm/visionos/tools/gen_visionos.py <build dir>` generates `<build dir>/xcode-visionos/DmVision.xcodeproj` from the prepared iOS project's `Gen/`, nxnative's `dm/ios/Sources` and `dm/visionos/Sources`. It is arm64 and device only, and shares the iPad build's bundle ID, so Documents (romfs.img, saves) survives. Source fixes for visionOS: the Launcher button style, `DM_SCREEN_SCALE` instead of `UIScreen`, no touch haptics or brightness, and `GCEventInteraction` + `shouldMonitorBackgroundEvents`. Without that interaction visionOS used the controller for system focus navigation, and only the D-pad appeared to work. iOS-compiled shader libraries load on the native visionOS app.
- **Immersive view** (`PortalVisionApp.swift`, `PortalCompositor.swift`, `vr_tap.m`): a SwiftUI entry point (`main.m` keeps `dm_vision_boot`) and a Full Space `CompositorLayer`. The present tap in `nvn_mtl.m` copies each presented frame into a ring texture and signals a shared event, and the window is not presented while VR is on. The composite maps each display pixel's ray (drawable view tangents) into the game's symmetric per-eye projection. The headset reports per-eye tangents h 1.732 / v 1.192 (symmetric hull), eye distance 63 mm and 1888×1792 eye textures.
- **Found on the way:** a frame whose `queryDrawable` returned nil must not be `endSubmission`ed (`BUG IN CLIENT` trap on leaving VR). The composite must write depth: a reverse-Z depth of only the clear (0) is shown black. It writes a constant 3 m for now.
- **First stereo result (user):** stereo visible, but blurry and judders with head motion. **Headset numbers** (Vision Pro M2, `sp_a1_intro1`, about 50 s in the immersive view): the game held 60 fps in stereo (frame time p50 16.7 / p95 17.5–18.5 ms), GPU p50 5.7–7.1 / p95 10.0–10.9 ms for both 960×1080 eyes; the composite ran at 90 Hz (4,652 frames), with 10 of 4,500 head poses missing at start. The game did not see head direction (tutorial look-up/down checks failed).
- **Next build:** the game's view angles follow the head (`IVEngineClient::SetViewAngles`, engine client vtable slots 18/19, checked against engine.nro's `CEngineClient` at `+0x921bc8`; the body yaw is the game yaw minus the head yaw set last frame). Each game frame carries the id of the head pose it was rendered with (a RenderView → present FIFO, `vr_view_take_rendered_pose`), and the compositor presents it with that pose's `DeviceAnchor`, so visionOS reprojects it to the display pose.
- **Blur:** each eye is 960×1080 spread over about ±60° × ±50°: about 8 px/degree. Raising it needs a larger game back buffer or render target, and/or an off-centre projection instead of the symmetric hull.

**Head-pose build, headset run (about 160 s in VR):** game view angles from the head are on (`IVEngineClient::SetViewAngles`), and 98% of composite frames are presented at the head pose the game frame was rendered with (the rest is the 3 s test grid). The user reports working head tracking and still-blurry eyes, with intermittent magenta rectangles (possibly right eye only).
- **Performance cliff:** the opening area held 60 fps in stereo (submit+present p50 2.4–2.9 ms, GPU p50 4.6–7.0 / p95 ~10 ms). From frame ~5,700 (the scene grows: 375–402 draws/frame, translated submit 83 → 144 M instructions, `MatQueue0` 352 ms/s) the game drops to about 30–36 fps in stereo: frame time p50 28–34 ms, submit+present p50 25–32 ms, GPU p50 9–11 / p95 15–18 ms. After leaving VR (mono) the same area runs frame time p50 ~18 ms, submit+present ~11 ms. The second RenderView doubles CPU-side material-system and submission work, and that, more than the GPU, is the headset's limit.
- **Magenta rectangles, cause and fix:** `DM_NVN_FB_SNAP=all` took no snapshot (Portal 2 has no same-pass feedback), and `DM_NVN_MAGSCAN` found no magenta block in any game pass during VR. Its only hits were near-black loading frames (R = B ≈ 0.004, a false positive). The user sees them only in VR, only while turning, and only in the heavier dilapidated-room scene. Cause: the first present tap copied the back buffer through a legacy command buffer (`q_cb`), which is ordered neither against the Metal 4 queue nor the encode thread, so it could read a frame mid-render. Fix: `nvn_mtl.m:mtl_tap_copy` copies on the Metal 4 queue behind the frame's work, with the same barriers, encode-thread path and event signal as `snap_take`; a ring slot whose previous copy is still running is skipped.
- (superseded) consistent with same-pass feedback sampling on Apple's tile GPUs (see `nvn_mtl.m` "Same-pass feedback sampling"). Diagnostic build: `DM_NVN_FB_SNAP=all` through the bundle's `dm/env.txt` (written into the prepared project's `Gen/dm/env.txt`; a new prepare removes it). The log names the shaders that sample their own attachment, for a `feedback_snap` profile entry.
